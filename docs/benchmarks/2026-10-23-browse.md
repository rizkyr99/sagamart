# Benchmark: browsing through the gateway

| | |
|---|---|
| **Date** | 2026-10-23 |
| **Issue** | [#33](https://github.com/rizkyr99/sagamart/issues/33) |
| **Target** | PRD §7 and testing strategy §3: product list and detail p99 < 200 ms, failures < 0.1%, at 500 VUs on a read-heavy mix |
| **Code measured** | `main` at `93bc244` plus this PR's test tooling (no service code changes apart from the gateway's warm-up SKU) |
| **Raw results** | [`raw/`](2026-10-23-browse/raw/): k6 summary JSON and output, `docker stats` and host samples, machine description |

## Question

Does browsing (product lists, product pages and carts) meet the PRD's read-latency target through the whole path? That path is the gateway (dev auth, rate limiting, composition), Catalog (Postgres, DynamoDB for carts) and Inventory (stock over gRPC, 150 ms budget).

## Result in one paragraph

**No: the target is missed by four to five times.** At 500 browsing users, p99 was **0.9–1.0 s** for lists and product pages (target 200 ms) and the median was about 350 ms, at about 335 requests/s with no failures. Pushed with no pauses, the stack peaked at **about 415 requests/s**, so 500 users who wait about a second between pages already ask for more than it can serve. Two things hold it there:

- **The gateway and Catalog each run their JavaScript on one thread, and both are saturated** (gateway ≈ 120%, Catalog ≈ 90% of a core). Inventory, Redis and DynamoDB are mostly idle.
- **About a third of the gateway's CPU goes to OpenTelemetry tracing.** Its own logic takes under 2%.

**The latency also hides a correctness-of-display problem.** About a quarter of pages rendered stock as `UNKNOWN`. Inventory was fast, but the busy gateway handled its answers after their 150 ms deadline.

## Environment

| | |
|---|---|
| Machine | Laptop, 13th Gen Intel Core i7-1355U (2 performance + 8 efficiency cores, 12 threads), 30 GB RAM |
| Stack | `make demo`: every service and its database in Docker Compose on the same machine, with the gateway's rate limit raised (below) |
| Services | One instance each: gateway and Catalog (NestJS 12, Node 24.11), Inventory (Go 1.27), Postgres 17, DynamoDB Local 2.5, Redis 7.4 |
| Tracing | On, as in normal use: every request traced (100%), exported to the OpenTelemetry collector and Jaeger |
| Load generator | k6 1.8.2 (`grafana/k6:1.8.2`) on the **same machine** over loopback (`--network host`) |

Everything shares one laptop, k6 included, so the numbers are a floor for this hardware, not a capacity figure. They are good for finding the bottleneck and comparing changes on the same machine.

## Method

[`deploy/k6/browse.js`](../../deploy/k6/browse.js), run through [`run-browse.sh`](../../deploy/k6/run-browse.sh), which also samples `docker stats`, free memory and load every few seconds.

- **Catalog:** each run's `setup()` creates 200 products with three SKUs each through the public admin API. Stock is spread across out (0), low (3) and in stock (40). Products accumulate, so the catalog grew from about 200 to 1,600 active products over the runs.
- **Buyers:** 500 VUs, ramped up over 30 s, held for 2 minutes, then ramped down over 10 s. Each request is one of:

  | Share | Request |
  |---|---|
  | 50% | A list: a random sort, half of them in the run's category; 20% then follow `nextCursor` to page two |
  | 35% | A product page, chosen at random |
  | 15% | Cart: half set a line in the VU's own guest cart, half read it |

- **Mix as recorded:** following a list to page two added a second list request to the same iteration. So the recorded runs were **55% list, 32% detail and 14% cart** by request, not the intended 50/35/15. Lists and product pages showed the same latency, so the conclusions don't change. `browse.js` now issues one request per iteration (page two follows the cursor from the buyer's previous list), so later runs get the intended mix.
- **Pacing:** each buyer pauses 0.5–1.5 s between requests (`THINK=1`), as a person reading pages would. A fourth run set `THINK=0` to find the most the stack can serve.
- **Rate limit:** raised to 100,000 requests/s for the runs (`GATEWAY_RATE_LIMIT_PER_SECOND`), because all VUs share one IP. The limiter still runs on every request, Redis call included; it just never refuses.
- **Pass/fail:** the k6 thresholds are the target: `http_req_duration{name:list}` and `{name:detail}` at p99 < 200 ms, and `http_req_failed` < 0.1%.

**A first attempt was discarded.** Jaeger, the local trace store, keeps every trace in memory with no limit by default. During that attempt it grew to 19 GB, and the machine ran out of memory (1 GB free, load average 92 on 12 threads), which made later runs and tests fail for reasons unrelated to the code. Compose now caps it (`MEMORY_MAX_TRACES=50000`). The runs below had at least 14.6 GB free throughout, with a load average of at most 8.3, and Jaeger stayed around 5 GB.

Throughput rose only from about 335 to 416 requests/s, while the median latency nearly tripled: requests were queueing. The failures were Catalog calls that missed the gateway's 1 s read deadline and came back as `503`; 109 such calls across the runs.

### Stock shown as `UNKNOWN`

Across the four runs, **52,628** stock lookups missed the 150 ms deadline, covering 1.87 million SKUs, against about 215,000 requests. That is roughly a quarter of the pages that show stock.

Inventory itself was far from busy (≈ 31% of a core, Postgres 14%). What missed the deadline was the gateway: with its one thread saturated, Inventory's answers waited in its queue until the deadline fired. The fallback did its job, since pages rendered and nothing failed, but it turned overload into wrong-looking stock rather than into latency.

### Where the gateway's CPU goes

A 60-second CPU profile of the gateway under the same load (taken before the machine ran short of memory), grouped by the nearest library on each sampled stack:

| Share | Where |
|---|---|
| **34%** | OpenTelemetry: spans for the HTTP server, Express, router, fetch and gRPC; context propagation; batching and OTLP export |
| 16% | Nest and Express routing and middleware |
| 9% | HTTP to Catalog (`fetch`/undici) |
| 9% | gRPC to Inventory (Connect over HTTP/2) |
| 9% | Node core: sockets, events, JSON |
| 9% | Logging (pino: one line per request, with redaction) |
| 5% | Redis rate-limit calls |
| 3.5% | Signing the internal identity (Ed25519; two per page) |
| 3% | Garbage collection |
| **1.6%** | The gateway's own code |

### Catalog's Postgres

The listing query is cheap. The heaviest one, an unfiltered price sort over 1,674 active products, executes in about 1 ms (a top-N heap sort, since the listing indexes lead with `category_id`). **Planning takes nearly as long (0.8 ms),** because Catalog's raw queries are planned on every call. With a list, a detail or a SKU lookup on every page, that makes Catalog's Postgres the third busy process.

## Analysis

- **One process per service is the limit, not the design of the calls.** Each page costs the gateway a fixed amount of single-threaded CPU, and at about 400 pages/s it has none left. Everything after that is queueing: latency rises, stock lookups miss their budget, and Catalog calls miss theirs.
- **Tracing every request at 100% is the largest single cost.** The PRD asks that 100% of requests carry a trace ID. That doesn't require recording and exporting 100% of spans: unsampled spans still have IDs for logs. Trimming instrumentation that adds spans without new information (Express and router layers on top of the HTTP span) is the other half.
- **More instances is the scaling answer, and it's already planned.** The services are stateless apart from their stores, so running the gateway and Catalog as several processes (a Node cluster, or replicas behind a load balancer) multiplies throughput. That's the Scale release (RFC-0004).
- **RFC-0005 §7's planned first lever, a Redis cache of Catalog's list and detail responses, would not fix this alone.** It takes load off Catalog and its Postgres, but the gateway, the tighter limit, would still do the same work per page.
- **The `UNKNOWN` stock under load is a product issue, not just a performance one.** A buyer sees "stock unknown" because the gateway is busy, not because Inventory is down. The `stock_unknown` counter makes it visible; an alert on its rate belongs with the SLOs.

## Not measured

- **Several instances per service** and a tuned Postgres: the Scale release.
- **Sampling and instrumentation changes:** only profiled here, not re-run. They are the cheapest experiment to try next.
- **A dedicated load-generator machine:** k6 shared the laptop's cores with the stack, which lowers the numbers.
- **The checkout path:** Stage 2.

## Reproducing

```bash
make identity-keys                                                                # once
GATEWAY_RATE_LIMIT_PER_SECOND=100000 GATEWAY_RATE_LIMIT_BURST=100000 make demo
for i in 1 2 3; do deploy/k6/run-browse.sh bench-results/browse users-run$i -e VUS=500 -e HOLD=2m; done
deploy/k6/run-browse.sh bench-results/browse throughput -e VUS=500 -e HOLD=1m -e THINK=0
python3 deploy/k6/summarize-browse.py bench-results/browse
make demo                                                                         # back to the normal rate limit
```

Each run adds 200 products to the local catalog.
